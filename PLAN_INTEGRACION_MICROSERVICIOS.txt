Proyecto: MultiliderNew
Fecha: 4 de noviembre de 2026, America/La_Paz
Versión del plan: 1.4
Estado: F0–F4 IMPLEMENTADAS y verificadas en ramas de trabajo. F5–F9 PENDIENTES.
Evidencias: pruebas/RESULTADOS_F0_F2.txt, RESULTADOS_F3.txt y RESULTADOS_F4.txt.
No se ha desplegado ni habilitado el modo remoto completo.
Alcance de este documento: diseño, secuencia y criterios de verificación.

1. OBJETIVO Y RESULTADO ESPERADO
========================================
Mantener un frontend Vue y un backend Laravel capaces de operar en dos despliegues:
- LOCAL: Laravel autentica y ejecuta las operaciones sobre sus datos locales.
- MICROSERVICIOS: Laravel conserva la API pública y delega cada dominio a
  Seguridad, Propiedades, Comercial y Finanzas.
El usuario utiliza las mismas pantallas. Las diferencias se resuelven mediante
adaptadores de backend, salvo estados nuevos que deban mostrarse, como una
operación pendiente de confirmación.
El modo se configura por instancia del backend. No se elige desde el navegador,
por una rama Git, por usuario ni automáticamente ante una caída.
Ambos modos se conservarán y probarán como funcionalidades soportadas.

2. PUNTO DE PARTIDA VERIFICADO (BASELINE ORIGINAL F0)
========================================
- backend: main; login local Sanctum, soporte JWT adicional, sincronizadores
  usuarios:sync y propiedades:sync, y actualización remota de disponibilidad.
- frontend: main y rama remota release/microservices. main utiliza Laravel.
  release/microservices consulta directamente Seguridad y Propiedades.
- Las ramas frontend divergen: la de microservicios no contiene todas las
  correcciones de main de correo de perfil, validación de propiedades y
  destinatarios de informes. No se debe hacer una sustitución ciega de ramas.
- Comercial y Finanzas existen junto a backend/frontend, tienen .sln, APIs,
  JWT, bases SQL Server propias, migraciones, Swagger y pruebas.
- Se verificaron 23 pruebas de esos dos servicios, con dobles HTTP y pruebas
  de migraciones/índices/concurrencia en SQL Server temporal.
  Esto NO certifica todavía el flujo real entre los cuatro servicios y Laravel.
- PEND-001 completado en F1/F2: en local no hay llamadas a microservicios,
  aunque el flag antiguo esté activo. Sincronizadores antiguos bloqueados.
- El frontend no tiene configurado actualmente un conjunto automatizado de
  pruebas de componentes/E2E comparable al que requiere este plan.

Brechas conocidas de los servicios nuevos que deben cerrarse antes del corte:
- Comercial consulta disponibilidad, pero Propiedades aún no ofrece reserva
  atómica. La unicidad local de una venta no protege a otros escritores.
- La inscripción de una venta en Finanzas es hoy un paso explícito.
- No hay un coordinador durable de los pasos distribuidos ni outbox.
- El PDF de contrato nuevo es un resumen/borrador, no la plantilla legal actual.
- Finanzas aún no incorpora Libélula ni todas las posibles variantes de pagos,
  anulaciones y recargos del sistema histórico. Se verificará la paridad real.
- El JWT manual de Laravel requiere revisar algoritmo, emisor, audiencia,
  vencimiento obligatorio y usuario activo.
- Los endpoints administrativos existentes de Seguridad/Propiedades requieren
  verificar permisos por operación; una autorización genérica no basta.

3. REGLAS DE ARQUITECTURA
========================================
3.1 Entrada única
Frontend -> Laravel -> implementación local o API del servicio.
El navegador deja de depender de las URL internas de los cuatro servicios.

3.2 Configuración
Introducir APP_ARCHITECTURE=local|microservices en config/architecture.php.
- Valor inicial y por defecto: local.
- Un valor desconocido debe producir un error de configuración identificable.
- En local, el arranque no exigirá claves JWT remotas, URL ni procesos .NET;
  se validarán únicamente las dependencias necesarias del modo seleccionado.
- Mantener secretos/URL en configuración del servidor, nunca en el frontend.
- Centralizar env() en archivos config antes de habilitar config:cache.
- Definir la relación con MICROSERVICE_SYNC_ENABLED: nunca podrá habilitar
  conexiones a microservicios si APP_ARCHITECTURE=local.
- En modo remoto, la sincronización antigua no seguirá sobrescribiendo tablas
  de negocio. Se retirará o sustituirá por proyecciones de lectura explícitas.
- Elegir el modo exige reiniciar/recargar workers, renovar sesiones y validar
  el estado de los datos. No será un interruptor de uso cotidiano.

3.3 Dos implementaciones detrás de un contrato
Crear contratos por dominio y resolver implementaciones mediante el contenedor:
  IdentidadGateway        Local / SeguridadHttp
  CatalogoGateway         Local / PropiedadesHttp
  ClientesAsesoresGateway Local / ComercialHttp
  VentasContratosGateway  Local / ComercialHttp
  CobranzasGateway        Local / FinanzasHttp
  MovimientosGateway      Local / FinanzasHttp
Los nombres son orientativos. Los controladores no acumularán condiciones de modo.
La implementación local debe reutilizar el comportamiento existente.
Los adaptadores remotos traducirán DTO, estados, errores y paginación.

3.4 Propiedad de datos
En local: Laravel conserva sus datos de negocio.
En remoto:
  Seguridad: identidad, credenciales, roles, permisos.
  Propiedades: catálogo, propietarios, disponibilidad, reservas e imágenes.
  Comercial: clientes, asesores, ventas, contratos y entregas.
  Finanzas: obligaciones, planes, cuotas, pagos, ingresos, egresos, comisiones.
Laravel conserva configuración empresarial, correo, coordinación y, si hacen
falta, proyecciones de lectura y equivalencias de identificadores.
Ningún servicio escribe directamente en la base de otro.
Los datos reflejados para consultas no serán un segundo origen de escritura.

3.5 Errores e idempotencia
No se confirmará una venta/pago que solo se guardó parcialmente.
No se ejecutará una escritura local como respaldo de una operación remota.
Cada comando reintentable tendrá un identificador persistente de operación.
Un timeout puede significar que el servicio sí confirmó: consultar/reconciliar
por identificador antes de repetir. No reintentar escrituras con un UUID nuevo.
Añadir tiempos máximos de conexión/respuesta, correlación y errores normalizados.
No registrar contraseñas, JWT completos ni datos personales innecesarios.

4. REPOSITORIOS Y RESPONSABILIDADES
========================================
backend:
  selección de modo, contratos/adaptadores, autenticación, coordinación,
  consultas de reportes/dashboard/portal, equivalencias y pruebas de ambos modos.
frontend:
  recuperar mejoras de ambas ramas, consumir una API común, unificar permisos,
  errores, identificadores de reintento y estados de procesamiento.
multilider-ms-seguridad:
  contratos de identidad, validación de permisos, perfil, credenciales,
  ciclo de vida de sesiones y pruebas con Laravel/otros servicios.
multilider-ms-propiedades:
  reservas/confirmación/liberación atómicas, autorización y migración de catálogo.
multilider-ms-comercial:
  integración real con reservas, estados de ventas, contratos/entregas,
  idempotencia, consultas y paridad funcional.
multilider-ms-finanzas:
  inscripción financiera, estados coordinados, paridad de cobros/reversiones,
  pasarela si corresponde, consultas y conciliación.
multilider-docs:
  contratos, decisiones, matriz de cobertura, migración y recuperación.

5. FLUJO DE RAMAS Y ENTORNOS
========================================
- main será estable en todos los repositorios.
- Durante implementación, crear ramas cortas por tarea, por ejemplo:
  backend: feature/modo-local y feature/adaptadores-ms.
  frontend: feature/frontend-unificado, basada inicialmente en main.
  servicios: feature/reservas, feature/ventas-coordinadas, etc.
- Conservar release/microservices como referencia mientras se recupera/adapta
  su trabajo. Integrar selectivamente; no perder funciones presentes en main.
- Revisar y probar cada cambio antes de fusionar. No hacer fusiones automáticas,
  reinicios del VPS ni actualizaciones Git por el simple hecho de publicar commits.
- Mantener dos instancias de validación con el mismo código backend:
  una local y otra microservicios, con configuraciones y datos aislados.
- Durante la transición, los parciales se prueban en integración; no se expone
  en producción una combinación arbitraria de dominios locales/remotos.
- Un cambio común de interfaz se implementa una vez y se prueba contra ambos modos.

 Operaciones comerciales/financieras coordinadas y reanudables.
Aceptación:

 No quedan ventas anunciadas como exitosas cuando sus pasos obligatorios fallaron.
 No existe doble comisión, doble ingreso ni mezcla de monedas.

8. CAMBIO DE MODO Y RECUPERACIÓN
========================================
Antes de habilitar escrituras remotas:
- Validar respaldos, manifiestos y destino de cada entidad.
- Pausar el origen antiguo, drenar colas, aplicar delta y conciliar.
- Seleccionar modo, invalidar sesiones incompatibles y reanudar con observación.

Si el problema aparece antes de aceptar escrituras nuevas:
- Se puede volver al despliegue anterior siguiendo el ensayo de recuperación.

Si ya hubo ventas/pagos nuevos en los servicios:
- NO basta cambiar APP_ARCHITECTURE=local ni restaurar únicamente el código.
- Pausar operaciones afectadas, identificar resultados confirmados y pendientes,
  conciliar, aplicar exportación inversa/delta si se decide volver y validar
  saldos/identificadores antes de reabrir.
- No eliminar cobros, cuotas ni documentos para forzar que coincidan conteos.
- Cada procedimiento debe indicar quién decide, evidencias y comandos concretos
  preparados para el entorno real, sin contraseñas en la documentación.
